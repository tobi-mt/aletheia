# Aletheia i18n Translation System - Construction Guide

## Overview

The Aletheia app uses a key-based translation system with English fallback. All user-facing text should be translatable to support 11 languages: English, Spanish, French, German, Portuguese, Arabic, Hausa, Igbo, Yoruba, Hindi, and Tagalog.

## How the i18n System Works

### Translation Function
```typescript
ts(translationKey: string, englishFallback: string): string
```

The `ts()` function:
1. Looks up `translationKey` in the current user's locale JSON file
2. If the key exists, returns the translated string
3. If the key is **missing**, returns the `englishFallback` parameter (English text displays to all users)
4. This behavior reveals incomplete translations immediately rather than silently failing

**Key Issue:** Missing translation keys cause all users to see English text, regardless of language selection.

### Locale Files Structure
- Location: `/src/locales/` 
- Files: `en.json`, `es.json`, `fr.json`, `de.json`, `pt.json`, `ar.json`, `ha.json`, `ig.json`, `yo.json`, `hi.json`, `tl.json`
- Format: Nested JSON objects with string values
- Requirement: **All 11 files must have identical key structure**, with native language translations for keys 2-11

## Adding New Translations

### Step 1: Add Translation Keys to English
When adding a new user-facing feature with text:

1. Open `/src/locales/en.json`
2. Add your new keys to the appropriate section or create a new section
3. Use meaningful key paths like `"featureName": { "subKey": "English text" }`
4. Follow existing naming conventions (camelCase, descriptive names)

**Example:**
```json
"newFeature": {
  "title": "New Feature Title",
  "description": "Feature description text",
  "buttonLabel": "Click here"
}
```

### Step 2: Update Component Code
In your React component, use the `ts()` function:

```typescript
import { useTranslations } from '@/lib/use-translations'; // or your i18n hook

export function MyComponent() {
  const { ts } = useTranslations();
  
  return (
    <div>
      <h1>{ts("newFeature.title", "New Feature Title")}</h1>
      <p>{ts("newFeature.description", "Feature description text")}</p>
      <button>{ts("newFeature.buttonLabel", "Click here")}</button>
    </div>
  );
}
```

### Step 3: Add Translations to All Other Locale Files
This is the **critical step** that prevents hardcoded text for non-English users.

For each of the 10 non-English locale files (es.json, fr.json, de.json, pt.json, ar.json, ha.json, ig.json, yo.json, hi.json, tl.json):

1. Open the file
2. Add the **exact same key structure** as English
3. Provide professional native-language translations

**Important:** The keys must be **identical** across all 11 files. Only the string values differ by language.

#### Professional Translation Resources
- Use professional translation services or:
  - Google Translate for initial draft
  - Native speaker review for accuracy
  - Translation management tools (Crowdin, Phrase, etc.)
- For context-aware translation, include usage in component code
- Test in-app to verify translations display correctly in narrow spaces

### Step 4: Validation
Before merging, run the validation script:

```bash
node scripts/validate-translations.mjs
# or
npm run validate:translations
```

Or validate manually:
```bash
python3 scripts/validate-translation-keys.py
```

## Validation Process

### Automated Validation Script
Create `/scripts/validate-translation-keys.py` to check all locale files:

```python
#!/usr/bin/env python3
import json
import os
import sys

def validate_translations():
    """Validate that all locale files have identical key structures."""
    locales_dir = './src/locales'
    languages = ['en', 'es', 'fr', 'de', 'pt', 'ar', 'ha', 'ig', 'yo', 'hi', 'tl']
    
    # Load all locale files
    all_locales = {}
    for lang in languages:
        filepath = os.path.join(locales_dir, f'{lang}.json')
        try:
            with open(filepath, 'r', encoding='utf-8') as f:
                all_locales[lang] = json.load(f)
        except FileNotFoundError:
            print(f"❌ ERROR: {filepath} not found")
            return False
        except json.JSONDecodeError as e:
            print(f"❌ ERROR: {filepath} has invalid JSON: {e}")
            return False
    
    # Get English keys as reference
    en_keys = set(all_locales['en'].keys())
    
    errors = []
    
    # Check each language
    for lang in languages[1:]:  # Skip English (reference)
        lang_keys = set(all_locales[lang].keys())
        
        missing = en_keys - lang_keys
        if missing:
            errors.append(f"🔴 {lang.upper()}: Missing keys: {missing}")
        
        extra = lang_keys - en_keys
        if extra:
            errors.append(f"🟡 {lang.upper()}: Extra keys: {extra}")
    
    if errors:
        print("Translation Validation Results:")
        for error in errors:
            print(error)
        return False
    else:
        print("✅ All translation files are consistent!")
        return True

if __name__ == '__main__':
    success = validate_translations()
    sys.exit(0 if success else 1)
```

### Manual Validation Checklist

When adding new translations:

- [ ] Feature code uses `ts("key", "English fallback")`
- [ ] New keys added to `/src/locales/en.json`
- [ ] New keys added to all 10 other locale files
- [ ] All locale files still have valid JSON (no syntax errors)
- [ ] Key structure is **identical** across all 11 files (only values differ)
- [ ] No missing comma or bracket issues
- [ ] Tested in app with different language selections
- [ ] Non-English text displays correctly (no English fallback text)
- [ ] Text renders properly in narrow spaces (mobile)

## Developer Workflow

### Adding a New Translation-Required Feature

1. **Plan** - Identify all user-facing strings that need translation
2. **Develop** - Write component code with `ts()` calls and English fallbacks
3. **Translate English** - Add complete nested structure to `en.json`
4. **Translate Others** - Add identical structure to all 10 other locale files with translations
5. **Validate** - Run validation script to check consistency
6. **Test** - Test in app with multiple language selections
7. **Review** - Have native speakers verify translations if possible
8. **Commit** - Include all 11 locale file changes in same commit

### Common Mistakes to Avoid

❌ **Don't:** Add keys only to `en.json` and commit without translations for other languages
- Result: All users of those languages see English text

❌ **Don't:** Use hardcoded strings instead of `ts()` function
- Result: Text doesn't support translation

❌ **Don't:** Have different key structures across locale files
- Result: Some translations never used, some keys missing in other languages

❌ **Don't:** Forget to test with non-English language selection
- Result: Bug discovered by real users in production

✅ **Do:** Add translations to all 11 files at the same time
✅ **Do:** Keep identical key structure across all files
✅ **Do:** Use `ts("key", "English fallback")` for all user text
✅ **Do:** Validate before merging
✅ **Do:** Test multiple languages before shipping

## Formation Practices Feature - Case Study

### What Went Wrong
The Reflect screen's "Formation Practices" (challenges) section displayed only English text for all users, regardless of language selection.

**Root Cause:** The entire `challenges` translation object (~40+ strings) existed only in `en.json` but was missing from all 10 other locale files.

**How it happened:** When adding the challenges feature, translations were added to English but not propagated to other languages before release.

### The Fix
Added complete `challenges` object with professional translations to:
- Spanish (es.json)
- French (fr.json)
- German (de.json)
- Portuguese (pt.json)
- Arabic (ar.json)
- Hausa (ha.json)
- Igbo (ig.json)
- Yoruba (yo.json)
- Hindi (hi.json)
- Tagalog (tl.json)

Each file now contains 20 nested translation keys for the challenges feature, matching the English structure exactly.

### Prevention
Following the workflow above will prevent this class of bug entirely.
