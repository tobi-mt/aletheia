# Copilot Instructions (Primary)

## Response Efficiency
- Prefer concise answers and minimal diffs.
- Avoid dumping large files unless requested.
- Do not create extra summary docs unless explicitly asked.

## Working Lens
- For every task, evaluate changes as a senior software engineer, a senior software test automation engineer, and a senior UX designer and engineer.
- Use that combined lens for implementation choices, test coverage, and user-facing behavior.

## Code Change Rules
- Preserve existing architecture and naming.
- Edit only what is needed for the task.
- Validate changed behavior with the smallest relevant check.
- Always update instruction files when project rules, workflow expectations, or agent behavior requirements change.

## UX Tooltip Rules
- Tooltips and info icons must be small and discreet by default (avoid large floating badges).
- Anchor tooltip triggers to card/section edges (prefer top-right corner), not inline in body copy.
- Use the shared tooltip pattern/component instead of custom one-off tooltip implementations.
- Keep tooltip overlays non-clipping and viewport-aware.
- When placing edge-anchored tooltip triggers, ensure the parent container is positioned for stable placement.
- Tooltip trigger buttons are exempt from global 44px touch-target rules; keep explicit compact sizing to avoid layout overlap.

## Horizontal Rail Rules
- Keep horizontal rails and compact chip trays single-line by default; labels should not wrap or overlap.
- Use a shared overflow-aware cue at the right edge only when more content actually exists, and hide it once the rail is fully scrolled.
- Preserve the active choice's visual clarity while keeping adjacent choices readable and untangled.
- Prefer the shared rail/cue pattern over one-off arrows, text hints, or decorative overlays.

## i18n Rules
- Keep translation key structure aligned across all locale files in [src/locales](src/locales).
- When adding a new key to [src/locales/en.json](src/locales/en.json), add it to all supported locales in the same change.
- Use and report results from `python3 scripts/validate-translation-keys.py` for translation work.
- Refer to [i18n.instruction.md](i18n.instruction.md) for complete translation workflow.
- Never introduce new user-facing English text in components, API payloads, notifications, or labels without a matching translation path.
- Prefer a single clear heading and a distinct body line per card or section; avoid repeating the same sentence or idea in adjacent copy blocks.

## Aletheia Design North Star
- See [README.md](README.md#aletheia-design-north-star) for the compact product guidance block.
- Keep UI changes aligned with serenity, decision-first clarity, Bible immersion, translation-first quality, wisdom-companion tone, and quiet-luxury styling.
- Avoid unnecessary repetition and nested layering in card-based surfaces; prefer one clear card or archive surface per section, and let individual cards expand in place when users need more detail.
- Keep pills and badges single-line and intentional: never let text break into stacked fragments, and do not repeat the same count or status in adjacent pills when one clear surface can carry it.
- Customizable formation practice cards must open their customization modal directly on tap, and modal close buttons should stay anchored in the top-right corner of the modal shell.
- Never expose code to the app.
- Never expose raw translation keys, placeholder tokens, or code-like identifiers in the app UI; every visible string must resolve through the translation path or a deliberate user-facing fallback.
- Never hardcode text in the app; Aletheia is fully translatable.
- Never repeat information unnecessarily.
- Never use pills when they are not relevant or needed.
- Pay attention to optimal UX flow.
- Keep first-run and onboarding screens especially lean: use the fewest words that still make the choice clear, and avoid repeating the same reassurance or setup message in multiple places.
- Formation flows should feel anchored, not jumpy: minimize automatic section switching or scroll chaining unless it materially improves orientation.
- Formation practice UIs should surface the next step, the shared plan, and the invite state in one coherent flow; if one section already explains it clearly, do not restate it again below.
- If a user has already created an account or is already signed in, do not surface onboarding again unless there is a deliberate account-specific reason.
